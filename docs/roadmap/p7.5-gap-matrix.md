# P7.5 console gap matrix

Audit of every console page against the Master Roadmap v3, P7.5 section 3, "Universal page anatomy", plus the shell items in section 1. It follows v3's instruction: audit first, and do not rewrite working pages blindly. The result decides what each P7.5 batch changes.

**Date:** 2026-10-16. **Baseline:** commit `272068c`, after batch 1 (seven-domain navigation).

## Method

- **All 35 navigation pages and both detail pages** were scanned in code for each criterion. Examples: `PageHeader` and `Guidance`, stat cards, search and filter controls, `DataTable`, empty/loading/error states, links, export and confirmation dialogs.
- **16 pages were screenshotted and reviewed** at 1440 px on the e2e backend. These were every mature (pre-page-kit) page plus a sample of page-kit pages: Command Center, Agents, Approvals, Tool Requests, Policies, Live Operations, Incident Center, Audit Trail, Risk Center, Sandbox, Settings, Service Accounts, Compliance Reports, Getting Started, Defensive Integrations and Notifications. The other page-kit pages share one structure, so they were judged from code.
- **Hand checks** covered whatever the scan could not settle: header actions, destructive actions, route guards and the agent registration flow.
- **Change history:** ◐ means the page lists past runs, deliveries or exports but not a record of configuration changes.
- The e2e backend holds almost no data, so the screenshots show empty and first-run states. Table density and behaviour under load are **not** assessed here. They need the synthetic demonstration organization (P7.5 item 11).

Legend: ✓ meets · ◐ partial · ✗ missing · – not applicable.

## Findings that need attention first

> **All four were fixed in P7.5 batch 2 (`4f4e8f7`).** See the batch 2 entry in `addendum-reconciliation.md`.

> **Progress since the audit:**
> - console design v2 (`52c0d93`) addressed visual consistency;
> - batch 3 (`edb8d36`) the role-preset Command Center;
> - batch 4 (`15c24f5`, `767b91f`, `efbe05a`) sorting and paging on the busiest lists, and evidence freshness on every page;
> - batch 4d (`3896adc`, `d6a1643`, `f294942`, `9338e77`) a server-side time range, URL-backed filters and personal saved views on the six evidence lists.
>
> - the Control Graph (`eabf0e1`, the interface in `6e381db`): an agent's related records, with exact decision provenance.
>
> Docs links remain open (they need hosted documentation). Related records now exist for agents through the Control Graph.

1. **Agents cannot be registered from the console.** `POST /agents` exists and issues the credential, but no page calls it. The Agents page's guidance starts with "Register an agent", and Getting Started's step "A first agent is registered" links to `/agents`, where there is no control for it. An administrator following the onboarding steps reaches a dead end. *Fix: a registration flow on Agents (name, minimum scopes, credential shown once), with a security review because it issues a credential.*
2. **Two shell indicators are static.**
   - The notification bell always shows its unread dot, even with nothing unread.
   - The sidebar's "Protected environment · Local control plane online" is fixed text, not a measured state.
   
   Both claim a status nobody checked. *Fix: bind both to real data (unread count; `/health` or the service components the Command Center already reads), or remove them.*
3. **Some empty lists read as "no results for your filter".** Incident Center ("No matching incidents"), Tool Requests ("No matching requests") and Audit Trail ("No matching evidence") show these messages even when nothing exists and no filter is set. A first-time user is told to change filters they never set. Page-kit pages such as Secrets and Service Accounts already separate the two cases.
4. **No shared permission-denied state.** No route guard exists. Each page handles a forbidden page its own way: a redirect to the Command Center (Abuse Protection), a read-only notice (Service Accounts, Agents), or an "Install operator access required" heading. The e2e permission suite covers these cases, so behaviour is safe, but the experience is inconsistent and v3 asks for one complete state.

## Page matrix

Columns (v3 section 3):
- **Purp.** Plain-language purpose: a header description plus how-to guidance.
- **Fresh.** Status and evidence freshness ("updated…", refresh interval).
- **KPI.** Two to five KPIs.
- **Act.** One page-level primary action. Refresh alone does not count. Queues whose real action is per row are marked ◐.
- **Find.** Search and filters.
- **Time.** Time range.
- **Views.** Saved views.
- **Table.** Sortable and paginated. ◐ means a custom list with no sort or paging, capped by an API `limit`.
- **States.** Empty, loading and error, with "nothing yet" separate from "no match".
- **Rel.** Links to related records.
- **Hist.** Change history.
- **Docs.** Link to the exact documentation section.
- **Exp.** Safe export.
- **Conf.** Confirmation for destructive actions.

## What the matrix says overall

- **Strong already:** every page has a plain-language purpose, and almost all have how-to guidance (P1.4). KPI rows exist nearly everywhere. Destructive actions are confirmed almost everywhere. Page-kit pages have complete empty/loading/error states.
- **Systemic gaps** (missing on nearly every page, so best solved once in the page kit, not page by page):
  - evidence freshness;
  - time range;
  - saved views;
  - related records;
  - contextual documentation links;
  - a page-level primary action. Most headers offer only Refresh.
- **The mature pages** (Agents, Approvals, Tool Requests, Policies, Risk Center, Live Operations, Incident Center, Audit Trail, Authentication, Sandbox) use custom lists with no sorting or paging, capped by an API `limit` of 200–500. They are also the busiest pages, so they matter most once real volume arrives.
- **Visual consistency:** stat cards, filter selects and empty states look different on the mature pages than on page-kit pages. Examples: large native selects on Incident Center and Audit Trail, compact ones on Agents, and four different stat-card styles. This is the design-quality batch's scope (v3 item 10), not a rewrite.

## Proposed order for the remaining P7.5 batches

This follows v3's ordering (`v3-adoption.md`, step 3) and puts the findings above first.

1. **Batch 2: corrections from this audit.**
   - Agent registration flow, under independent security review because it issues a credential.
   - Real data behind the bell dot and the posture text.
   - Separate "nothing yet" from "no match" on the three pages.
   - A shared permission-denied state.
   - The Sandbox empty panel.
2. **Batch 3: role-preset Command Center.** v3 item 2: presets for the six roles, per-user pinning, and only what the user may see.
3. **Batch 4: page-anatomy kit, then adoption.**
   - Add freshness, primary-action and related-records slots to `PageHeader`.
   - Add a time range and saved views to `FilterBar`.
   - Add a "Docs" link to `Guidance`.
   - Move the mature pages' lists onto `DataTable`, which brings sort and paging.
   - Adopt page by page, mature pages first.
4. **Batch 5 onward:** the Control Graph, the investigation workspace and decision explainability, in v3's order. The NEW security-sensitive items each get their own design and review first.

Nothing in this audit changed code.
