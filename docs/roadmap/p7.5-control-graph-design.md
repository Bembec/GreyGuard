# P7.5 Control Graph: design for review

**Status:** approved by the owner on 2026-10-16, with the decisions below. Being built.
**Needs before building:** the owner's go-ahead and an independent security review. It adds a read endpoint that joins records across tables, so its permission and tenant filtering must be right on every node.
**Source:** Master Roadmap v3, P7.5 item 4, as adjusted in v3 section 3:

> Scope to an agent-centred relationship view built from existing records, with server-side permission and tenant filtering on every node, depth and size limits, and no new graph database.

## The questions it answers

For one agent, an administrator should be able to answer from one screen:

1. **What may this agent do?** Its identity, credential state, scopes, the tools those scopes reach, and the controls currently limiting them.
2. **Why was this decided?** For any request: the decision, the rule that matched, and the approval, if any.
3. **Which policy version?** The version that was in force when the request was decided.
4. **Which identity?** The credential or certificate the request authenticated with.
5. **What is related?** The approvals, incidents and evidence that touch the agent or one of its requests.
6. **What would a change affect?** For example, revoking a scope or a credential: which tools and recent request patterns would stop working. This is shown as a preview only; the change itself still happens on its own page.

## What exists today (surveyed)

| Relationship | Where it lives | Tenant column | Notes |
|---|---|---|---|
| Organization → agent | `agent_runtime_states`, the identity table | `org_id` | Names are global; ownership is checked by `require_agent_in_org`. |
| Agent → identity, credential, scopes | the identity table, credential history | `org_id` | Already returned by `GET /agents/{name}/investigation`. |
| Scope → tool action | `main.permissions` (the action catalogue), `adapter_configs`, `universal_capability_controls`, `capability_removals` | catalogue global; controls per org | Tool catalogue is code; per-org controls are rows. |
| Agent → request | `tool_requests` (`agent_name`) | `org_id` | Indexed by (`agent_name`, `timestamp`). |
| Request → decision | `tool_requests.policy_decision`, `risk_added` | `org_id` | Decision is stored; **the matched rule and policy version are not.** |
| Request → approval | `approval_events` (`request_id`) | `org_id` | Reviewer, time and note. |
| Agent or request → incident | `security_alerts` (`agent_name`, `request_id`) | `org_id` | |
| Anything → evidence | `audit_events` (`agent_name`, request id in details), `audit_integrity_chain` | `org_id` | |
| Policy versions | `policy_versions` (`published_at`, `supersedes_policy_id`) | `org_id` | |

`GET /agents/{name}/investigation` (`backend/app/agent_investigation.py`) already gathers identity, risk, authentication history and requests for one agent, scoped to the caller's organization. The graph extends that function rather than starting a second path.

### A gap this design must close honestly

A tool request does **not** record which policy version decided it. Today the version can only be **inferred**: it is the version published most recently before the request's timestamp. That inference is usually right, but it can be wrong around a publication, or if a rollout was staged.

**Proposal:**
- Add a `policy_version_id` column to `tool_requests`, written when the decision is made. This needs an Alembic migration, rehearsed both ways on PostgreSQL per the verification bar.
- Add `matched_rule` the same way, so "why" is a record, not a reconstruction.
- Requests decided before the migration show the version as **"inferred from publication time"**, visibly labelled, and never as fact. This follows v3's rule: no invented certainty.

## API

```
GET /agents/{agent_name}/graph?depth=2&limit=200
```

- **Authentication:** `require_admin`. The permission is `read`, the same as the investigation view. Every role may read it, because it shows only records the caller could already open one by one.
- **Tenant scope:** `require_agent_in_org(agent_name, administrator)` first, then **every query** passes the caller's `org_id`. No node is ever fetched by id alone. A node from another organization is impossible by construction, not filtered after the fact.
- **Permission filtering per node:** nodes from install-wide sources (gateway nodes, install-level audit integrity) are included only for install operators. Otherwise they are counted as `"withheld": n` with the reason "install operator access required", so the graph never pretends they do not exist and never leaks their contents.
- **Limits:**
  - `depth` is 1 or 2 (agent → direct records, or one more hop: request → approval, incident, evidence). The default is 2.
  - `limit` defaults to 200 nodes, and 500 is the hard maximum.
  - Requests are taken newest first within a window of 30 days by default.
  - When a limit cuts the graph, the response says so (`"truncated": true` with counts per type) and the UI offers the filtered list page instead.
- **Rate limits:** the general API bucket applies. The response is cached for 15 seconds per (org, agent, depth, limit).
  - **Deviation DEV-001 (open):** the 15-second cache is not built yet. It is tracked with an owner and a follow-up task in `deviations.md` (FU-CG-01).

- Payloads, targets and notes are **summarised, never returned raw**, exactly as the investigation view already redacts them.
- Secrets are never nodes: a secret reference appears as its name only, and only to roles that may read the Secrets page.

## Interface

- A **"Relationships"** tab on the agent's investigation page (`/agents/:name`). No new navigation item is needed.
- **Layout:** five fixed columns that read left to right, rather than a free-floating force graph:
  1. identity and credential;
  2. scopes;
  3. tools and controls;
  4. requests, grouped by decision;
  5. outcomes: approvals, incidents and evidence.

  Selecting any node highlights its path and opens a side panel with its facts and a link to its own page. Force-directed graphs look impressive and read badly. Column flow matches how the gateway actually decides, and works on a phone as stacked sections.
- **Accessibility:** every node is a real button in reading order, and the side panel is the same content as a list. The whole view has a text alternative ("Relationships as a list").
- **"What would a change affect":** a "Preview impact" toggle on a scope, credential or tool node. It lists the tools that would become unreachable and the requests from the last 30 days that would now be refused. It reads only; the change itself stays on the Agents or Policies page, under its own confirmation.

## Tests

- **Backend.** Each node type is returned only for the caller's org. A second org's agent with the same request ids is never joined in. Install-level nodes are withheld for non-operators and counted. Depth and limit are enforced and `truncated` is set. Inferred versus recorded policy versions are labelled. No raw payload or secret value appears.
- **Mutation checks** on the org filter, the withheld rule and the limits.
- **Migration** for `policy_version_id` and `matched_rule`, rehearsed upgrade and downgrade on postgres:17-alpine.
- **Frontend:** the reading order and side panel work from the keyboard, the impact preview reads only, and the page fits at 390 px.

## Out of scope

- A graph across all agents, or across organizations.
- Editing from the graph.
- A graph database.
- Confidence scores (v3 removed them).

## Owner decisions (2026-10-16)

1. **History window.** 30 days by default. Another range may be chosen only within data the organization still retains. The graph never implies that older history exists once it has expired under retention: the response states the retained horizon and the UI says "Older history is not retained", not "load more".
2. **Exact policy-decision history.** Every new request records, at decision time:
   - `policy_version_id`;
   - a stable `matched_rule_id`, plus the matched rule's name and type where useful;
   - the decision outcome;
   - an immutable fingerprint (SHA-256 over the canonical rule and the version's content) and an evidence snapshot of the matched rule, enough to verify the historical decision without trusting a mutable policy record.

   Requests decided before this change stay labelled **"inferred"**. The UI always distinguishes exact evidence from inferred history.
3. **Auditor impact preview.** Auditors may use the impact preview, only for organizations and records they may read. Their experience is explicitly read-only: no saving or activating policies, no approval actions, no rollback, no mutation through direct API calls, and clear read-only labelling. Negative authorization and tenant-isolation tests prove it.

**Constraints restated by the owner:** do not weaken existing evidence immutability or retention controls. Tests cover backend, frontend, PostgreSQL, tenant isolation, authorization and historical evidence.

## Original open questions (answered above)

1. Should the window be 30 days by default, or follow the organization's retention setting?
2. Is recording `policy_version_id` and `matched_rule` on every request acceptable? It is a schema change, and it makes decision explainability (v3 item 6) exact instead of inferred. Recommended: yes.
3. Should auditors see the impact preview? It reveals nothing they cannot already read, but it is framed as a change tool. Recommended: yes, labelled read-only.
