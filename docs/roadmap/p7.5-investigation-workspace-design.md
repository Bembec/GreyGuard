# P7.5 Investigation workspace and decision explainability: design for review

**Status:** approved by the owner on 2026-10-16, taking every recommendation below ("go with your recommendation"). Being built.
**Source:** Master Roadmap v3, P7.5 items 5 and 6:

> **5. Investigation workspace.** Severity, status, owner, SLA, timeline, context, related decisions and approvals, evidence integrity, notes, containment actions, exportable incident package, full action record.
>
> **6. Decision explainability.** Decision, plain-language reason, policy and version, matched rules, identity and authentication assurance, requested capability and resource, approval path, recommended next step, known limitations. No invented confidence score. "Why am I seeing this?" and "Why is this unavailable?" without leaking restricted details.

They are designed together because an investigation is mostly a set of decisions to explain.

## What exists today (surveyed)

| Need | Today | Gap |
|---|---|---|
| Incident record | `security_alerts`: severity, status (OPEN, ACKNOWLEDGED, INVESTIGATING, RESOLVED, DISMISSED), `assigned_to`, `resolution_note`, evidence JSON, org-scoped. Notes in `alert_notes`. | `assigned_to` is free text, not a person. No SLA. Status changes are not recorded unless a note is attached. Incidents are opened in a modal on Incident Center, not on a page of their own. |
| Request explanation | `/request-investigations/{id}`, rendered on `/requests/:id`: a generic sentence, a timeline, the redacted payload. | `explain_decision()` guesses from status. It calls an emergency refusal "the active policy does not permit this action", which is wrong. Exact decision records (Control Graph, `eabf0e1`) now make an exact explanation possible. |
| Decision provenance | `decision_records`: version, matched rule, outcome, fingerprints. | Not yet used by any explanation. |
| Identity assurance | Authentication events are recorded per attempt (key or certificate). | Not linked to the request they authenticated. |
| Containment | Separate routes: credential revoke, agent reset, emergency controls (global deny, disabled agents and tools), isolation terminate. Each has its own permission check. | Not reachable from an incident. Nothing links an action to the incident it was taken for. |
| Evidence integrity | Install-wide audit chain; decision-record fingerprints. Verifying the chain is install-operator only. | No per-incident integrity statement. |
| Export | Request bundle download (built in the browser). Compliance reports. | No incident package, and no server-side record of who exported what. |

## Page structure

### 1. Incident workspace: `/incidents/:alertId` (new page)

Incident Center keeps its list. A row opens this page instead of the modal, so an incident has a link that can be shared.

- **Header** (page-kit `PageHeader`):
  - title; severity and status badges; owner; SLA state;
  - one primary action, chosen by state and permission: Acknowledge, then Investigate, then Resolve.
  - Secondary: "Export package", "Copy link".
- **Main column: the timeline** (below).
- **Right rail, top to bottom:**
  1. **What happened.** The triggering decision's explanation card (section 3).
  2. **Agent and actor.** The agent, its status, credential state and scopes, with a link to its Control Graph. The actor: the agent name, and for approvals the reviewer.
  3. **Related.** Other incidents for the same agent or request; the decisions and approvals in the incident's window. Each is a link.
  4. **Evidence integrity** (below).
  5. **Containment.** Permitted actions (below).
- **Notes:** add a note (incident:manage). Notes appear in the timeline.

### 2. Request page `/requests/:id`: explanation upgraded

The generic sentence is replaced by the explanation card (section 3), followed by the existing timeline and redacted evidence. The same card is used in the workspace, the Control Graph's panel and the approval review.

### 3. The explanation card (decision explainability)

One component, fed by one endpoint. Every field shows its basis, recorded or inferred, never mixing the two.

| Field | Source | Example |
|---|---|---|
| Decision | `decision_records.outcome` | **BLOCK** |
| Plain-language reason | Deterministic text per rule type and outcome: one sentence per case, written and reviewed, never generated | "Blocked because `send_email` is not allowed by policy v4." / "Refused because the emergency global deny was on." |
| Policy and version | the record's version, linked; for requests without a record: "inferred: v3, from publication time" | Policy v4 (published 12 Oct) |
| Matched rule | `matched_rule_id`, name, type, snapshot | `permission:send_email` → BLOCK, risk weight 40 |
| Identity and authentication assurance | **New:** the authentication method recorded on the decision record: agent key, or a verified client certificate. Older requests: "not recorded". | "Authenticated with a verified client certificate." |
| Requested capability and resource | action, target (shortened), dry run | `write_note` on `notes/todo.txt` |
| Approval path | ASK → reviewer, decision, time; or "no approval needed (ALLOW)" | Approved by A. Admin, 14:02 |
| Recommended next step | Deterministic per state (table below) | "If this action is legitimate for this agent, propose a policy change." |
| Known limitations | Fixed, honest statements that apply | "GreyGuard sees the tool request, not the model's prompt." |
| Integrity | the record matches its fingerprint; the policy version is unchanged | ✓ / ⚠ with wording |

No confidence score anywhere. Decisions are deterministic.

**Recommended next steps (deterministic):**

| Situation | Next step shown |
|---|---|
| ASK, pending, viewer may approve | "Review it in Approvals." |
| ASK, pending, viewer may not approve | "Waiting for a reviewer with approval rights." |
| BLOCK by a listed rule | "If this is legitimate for this agent, propose a policy change in Policies." |
| BLOCK by the default rule (unlisted action) | "This action is not in the policy. Add it explicitly if it should be allowed or asked." |
| REFUSED by an emergency control | "An emergency control is on. It stays on until someone with policy rights turns it off." |
| REFUSED, agent suspended | "Investigate the agent, then reset it from its page if it is safe." |
| ALLOW, execution failed | "The policy allowed it; the tool failed. See the execution result." |

**"Why am I seeing this?"** A short line on every explanation and incident, for example: "You see this because you can read your organization's evidence."

**"Why is this unavailable?"** Every action the viewer cannot take is shown disabled, with a reason built only from the viewer's own role. For example: "Your role, Auditor, can view incidents but not change them." It never names the record or person that blocks it, and never reveals withheld content. Install-level items are counted, as in the Control Graph.

### 4. The investigation timeline

One ordered stream for the incident's window (by default from 24 hours before the trigger to now, bounded by retention), merging:
- the triggering evidence and the request's decision;
- approvals and executions;
- the agent's other decisions in the window (collapsible);
- authentication failures for the agent;
- incident events: status changes, assignment, notes, containment actions, exports.

Each entry has a type icon, the time (with its UTC offset on hover), the actor, one sentence, and a link to its own record. Filters: type, actor. Entries are paged ("Show more"), newest first, with "Jump to trigger".

### 5. Evidence integrity, per incident

- The triggering request's decision record matches its fingerprint (computed for any reader).
- The policy version that decided is unchanged since.
- Audit chain: install operators can run a verification from here (the existing route). Everyone else sees when the chain was last verified and its result, read-only.
- Anything not verifiable is labelled as such ("No decision record: decided before records existed").

### 6. Permitted actions (containment), and the full action record

| Action | Permission (server-side, unchanged from its existing route) | Confirmation |
|---|---|---|
| Acknowledge / Investigate / Resolve / Dismiss, assign owner, add note | `incident:manage` | Resolve and Dismiss need a note |
| Revoke the agent's credential | `identity:manage` (as `/agents/{name}/credential/revoke`) | Typed confirmation, reason |
| Emergency-disable the agent or the tool | policy-editor rights (as `/policy-emergency-controls`) | Confirmation, reason |
| Terminate isolated execution | its existing guard | Confirmation, reason |
| Export incident package | `read` | None; recorded |

- Actions go through one route, `POST /incidents/{id}/actions`. It applies **the same guard as the underlying route**, calls the same function, and appends an `incident_events` row (append-only, with a trigger as for decision records) with the actor, action, reason and result.
- The existing routes are unchanged. Using them directly keeps working, and is linked to no incident.
- Approval decisions are not taken here: the workspace links to the approval review, which has its own four-eyes rules.
- **Full action record:** `incident_events` captures every status change (today only notes are recorded), assignment, note, containment action and export, with actor and time. It is shown in the timeline and included in the package.

### 7. Exportable incident package

`POST /incidents/{id}/package` (a POST because it records the export) returns a JSON package:
- the incident;
- its timeline;
- explanation cards;
- decision records with their fingerprints;
- the action record;
- the integrity statement;
- a manifest with a SHA-256 over each part and over the whole.

It holds redacted evidence only, and nothing withheld from the viewer. The export is recorded as an incident event. PDF and print come later, with V2's print-friendly reports.

## Owner and SLA

- **Owner:** a member of the organization, chosen from its member list, never free text. Existing free-text values are shown as "legacy owner: …" until reassigned.
- **SLA:** targets per severity, set per organization. Until an organization sets them, the page shows "No SLA set". It never shows an invented deadline. States are: within target, due soon (last 25%), breached. Breaches appear in the timeline and on Incident Center. Proposed defaults are an owner decision (question 2).

| | Platform admin | Security analyst | Auditor | Install operator (extra) |
|---|---|---|---|---|
| See workspace, timeline, explanations | ✓ | ✓ | ✓ | + install-level incidents |
| Notes, status, owner | ✓ | ✓ | disabled, with reason | |
| Containment actions | per action's existing guard | per guard (no credential revoke unless identity:manage) | disabled, with reason | |
| Export package | ✓ | ✓ | ✓ (recorded) | |
| Run chain verification | | | | ✓ |

## Tenant isolation

- **Org-scoped reads:** every read is scoped by the caller's org, as in the Control Graph. A foreign or missing incident is the same 404.
- **Related records:** related incidents, decisions and timeline entries are fetched with the org filter; install-level ones follow `alerts._visibility()`.
- **Containment through the workspace:** the incident's org must equal the caller's, and the target agent must belong to that org (`require_agent_in_org`). Otherwise 404, and nothing is recorded.
- **The package** contains only the caller's org's records.
- **New tables:** `incident_events` and the SLA settings join the tenant guard's org-scoped registry, with migrations rehearsed on PostgreSQL.

## Loading, empty and error states

- **Independent sections:** each section loads on its own with a skeleton. One failed section shows its own error with Retry and never blanks the page.
- **Empty states say exactly what is empty:** "No notes yet", "No related incidents in this window", "No decision record: decided before records existed".
- **Not found:** a missing or foreign incident gets the shared not-found state, with no hint which of the two it is.
- **Permission denied:** a page the role may not open gets the shared access-denied state (batch 2).
- **Offline:** the shell's offline banner applies, and actions are disabled while offline.

## Mobile

- **Single column:** the header, then "What happened", then the timeline, then the rail sections as collapsible panels.
- **Sticky bottom bar:** the primary action and "More actions", which opens a sheet.
- **Timeline** entries wrap, and their links are full-width tap targets.
- **Verified at 390 px** wide with screenshots, and from the keyboard.

| `/incidents/{id}/actions` | POST | the underlying action's guard | Appends to `incident_events`. |

## Schema changes

1. **`incident_events`:** append-only, org-scoped. One row per status change, assignment, note, containment action and export.
2. **`decision_records`, schema version 2:** adds `authentication_method`. New records only; version-1 records show "not recorded". The table stays append-only.
3. **`incident_sla_targets`:** org-scoped. Only if question 2 is approved.

Each change gets an Alembic migration, rehearsed both ways on PostgreSQL.

## Owner decisions (2026-10-16): all recommendations accepted

1. **Containment from the workspace:** yes. Revoke credential, emergency-disable an agent or tool, and terminate isolation, each with the same guard as its existing route, a typed confirmation and a recorded reason. Approval decisions stay in the approval review.
2. **SLA:** no defaults. "No SLA set" until an organization configures targets. The proposed values are offered as suggestions at that point.
3. **Authentication assurance:** record the authentication method on new decision records (schema version 2). Older records say "not recorded".
4. **Auditor exports:** allowed, and every export is recorded.
5. **Payload display:** values that look like secrets are redacted for every role, and the redaction is labelled.

## Original open questions (answered above)

1. **Containment from the workspace.** Allow revoke credential, emergency-disable agent or tool, and terminate isolation from the incident, each with the same guard as today, a typed confirmation and a recorded reason? *Recommended: yes.* Approval decisions stay in the approval review.
2. **SLA.** Per-organization targets by severity. Proposed defaults: Critical, acknowledge in 15 minutes and resolve in 4 hours; High, 1 hour and 24 hours; others none. Or ship with no defaults ("No SLA set" until configured)? *Recommended: no defaults.* Offer these as suggestions when an admin first configures SLAs, so GreyGuard never implies a commitment nobody made.
3. **Authentication assurance on new decisions.** Record the authentication method (agent key or verified certificate) on each new decision record (schema version 2)? *Recommended: yes.* Older records stay "not recorded".
4. **Auditor exports.** Auditors may export incident packages, with each export recorded? *Recommended: yes.*
5. **Payload display.** Today the request page shows payload values, redacted only by key name. Also redact values that look like secrets (tokens, keys, JWTs) for every role, and label the redaction? *Recommended: yes.*
