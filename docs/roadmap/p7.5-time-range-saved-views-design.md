# P7.5 Time range and saved views: design for review

**Status:** proposed design, 2026-10-16. Nothing is built.
**Why a design first:** the addendum's batch 4 record says these need their own design, covering which pages get them, server-side time filters, and where views are stored (`addendum-reconciliation.md`, line 715).
**Source:** the gap matrix's systemic gaps (`p7.5-gap-matrix.md`), batch 4: "Add a time range and saved views to `FilterBar`."

## What exists today (surveyed)

- **No list endpoint accepts a time filter.** `GET /tool-requests`, `/audit-events`, `/alerts` and `/live-events` return the newest N rows (`limit`, capped at 200 to 500), filtered by status, type or agent and always by `org_id`.
- **So a time range cannot be done in the browser.** Filtering the newest 200 rows by date would quietly hide older matching evidence. That breaks the honesty rule: the page would look complete when it isn't.
- **Indexes.** `tool_requests` has (`agent_name`, `timestamp`), (`approval_status`, `timestamp`) and (`execution_status`, `timestamp`). `authentication_events` is indexed by agent. `audit_events` and `security_alerts` have no time index.
- **Filter state lives in component state.** Only Agents reads the URL (`?register=1`). A filtered view can't be bookmarked, shared or restored with Back.
- **Per-user preferences already have a precedent.** Command Center presets and pins are stored in `localStorage` under a key that includes `admin_id`, and are treated as a convenience: if storage is blocked, the choice lasts for the visit.
- **Rate limit.** The e2e suite and real users share the GENERAL 300/min limit. A time-range change must cost one request, not one per panel.

## Proposal

### 1. Server-side time range

- **Parameters.** Add optional `since` and `until` (ISO 8601, timezone required, normalized to UTC) to the three evidence list endpoints: `/tool-requests`, `/audit-events` and `/alerts`. The Authentication page reads `/audit-events?event_type=AUTHENTICATION`, and Approvals reads `/tool-requests`, so these three cover all six pages.
- **Validation.** Reject a missing timezone, `until` ≤ `since`, and a span over 400 days, with a 422 that names the problem. No range means today's behaviour, so existing clients are unaffected.
- **Applied in SQL, after the org filter.** It narrows the tenant-scoped query and never replaces it. Parameters are bound and never formatted into SQL.
- **Honest totals.** Each response gains `range: {since, until}` and `truncated: true` when the row cap was hit inside the range. `FilterBar`'s summary then reads "Newest 200 of more in this range. Narrow the range to see older evidence." The page never presents a capped list as complete.
- **Indexes.** One Alembic migration adds `(org_id, timestamp)` indexes to `audit_events` and `security_alerts`. It is rehearsed up and down on postgres:17-alpine, per the verification bar.
- **Live Operations.** The stream stays live. The range applies only to its initial history load, and the page says so.

### 2. One control in `FilterBar`

- **Presets.** "Last hour", "24 hours", "7 days" and "30 days", plus a custom range (two `datetime-local` inputs showing the viewer's timezone, sent as UTC).
- **Open work is never hidden by a range.** A pending approval or an open incident always shows, however old. On Approvals and Incident Center the range applies only to decided or resolved history. Otherwise a 24-hour default would quietly drop a request that has waited two days, which is exactly the item that most needs attention.
- **Default.** 24 hours on Tool Requests and Live Operations; 7 days on Audit Trail, Authentication, and the history sections of Approvals and Incident Center. Every page shows its active range, so nobody mistakes "nothing in 24 hours" for "nothing ever". The empty state says "Nothing in the last 24 hours" and offers "Widen to 30 days".
- **Where.** Time-based evidence lists only: Tool Requests, Approvals, Audit Trail, Incident Center, Authentication, and Live Operations' history. **Not** on configuration pages (Agents, Policies, Secrets, integrations), where "when" isn't the question. Compliance Reports keeps its own report period.

### 3. Filters in the URL

- Every filter on those pages, including the range, moves into the query string, for example `?range=7d&status=PENDING&agent=billing-bot`.
- Relative ranges stay relative (`range=24h`), so a bookmark means "the last 24 hours" whenever it's opened. Custom ranges are absolute (`since=…&until=…`).
- Back and Forward then work, and a link pasted to a teammate opens the same view. Opening the link still needs their own sign-in, permissions and org: the URL carries no authority.
- Unknown or invalid values fall back to the page default and are dropped from the URL. A bad link never errors.

### 4. Saved views, version 1: personal

- **What a view is.** A name plus a page's query string, for example "Pending, billing agents, 7 days".
- **Where.** A "Views" menu in `FilterBar`: save the current view, apply one, rename, delete. A maximum of 20 per page.
- **Storage.** `localStorage`, keyed by `admin_id` and page, exactly like Command Center pins. That means no backend change, no new data to protect, and nothing that can leak across tenants. The trade-off: views don't follow the user to another browser. The menu says "Saved in this browser".
- **Org switching.** Views hold filters, not data. Applying one in another org shows that org's records, filtered the same way.

### 5. Later, not in this batch: shared team views

Shared views need a server table (`org_id`, `owner_admin_id`, page, name, query, visibility), role checks on create, edit and delete, and audit events. That is a new security-sensitive surface, so it gets its own design and review. Version 1's view format (a page plus a query string) is chosen so it can be migrated into that table unchanged.

## Build plan (once approved)

1. **4d-1, backend.** `since`/`until`/`truncated` on the three endpoints; migration for the two indexes; tests for validation, open items ignoring the range, org isolation with a range (org A's range never returns org B's rows), truncation, and the no-range default. Mutation checks on the org filter and the span limit.
2. **4d-2, frontend.** `TimeRange` control in `FilterBar`, URL-backed filter state hook, adoption on the six pages, honest "newest N" summaries, and range-aware empty states.
3. **4d-3, saved views.** The Views menu, `localStorage` store with unit tests for blocked storage and malformed entries, and e2e: save, reload, apply, delete.
4. **Docs.** One `docs:` commit recording the full verification run in the matrix.

Each step stays well under the GENERAL rate limit: one request per range change, with no extra shell requests.

## Open questions for the owner

1. **Defaults.** 24 hours on Tool Requests and Live Operations, 7 days elsewhere, with open approvals and incidents always shown? Recommended: yes.
2. **Personal views first, shared later?** Recommended: yes. Personal views ship without new backend surface; shared views get their own design and review.
3. **Maximum custom span.** 400 days, so a full year's audit can be reviewed in one range? Or should it follow the organization's retention setting? Recommended: 400 days now, retention-aware once retention is configurable per org.

None of these blocks the backend step, which is the same under every answer except the span limit, and that is one constant.
